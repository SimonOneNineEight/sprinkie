# Beta data is durable from the first TestFlight build

The TestFlight beta (#16) runs against the hosted Supabase project that already backs device builds, and its data is real from the PM's first Entry: forward migrations only, no destructive migration, no reset, no wipe before public launch. The cheaper option was on the table and rejected — announce up front that beta data may be reset, and buy back the freedom to drop and recreate whenever a schema change is awkward. Two testers and a few weeks of Entries is a trivial amount of data to protect, so the reason is not the data's volume:

1. A Journal that people expect to lose gets written in differently. The beta exists to find out whether a person will spend a few minutes a day on this for weeks, and that question only has an honest answer if the days they write are days they keep. A reset clause converts every tester into someone trying the app rather than using it, which is the one signal the beta cannot buy anywhere else.
2. The promise cannot be walked back. By the time a destructive migration is tempting, the PM has a month in there, and "we said it might be reset" is technically true and relationship-ending. The decision is therefore made now, while it costs nothing, rather than under pressure from a migration that would be easier destructively.
3. A separate TestFlight-only project was the third option and buys real isolation, at the price of every migration applied twice, two sets of secrets, and two API configurations to keep in step — for a two-person ring. The isolation protects against exactly the destructive migrations this ADR forbids anyway.

The consequence lands on ADR-0004, which deferred E2EE partly because "MVP threat reality is a TestFlight cohort where conventional security covers the actual risks." The cohort stays small, but its Journals are now durable, so the never-log-content rule and strict per-user authorization are carrying real content rather than throwaway test rows. ADR-0004's pre-launch E2EE checkpoint also arrives with populated Journals already in the database: a later rollout has to migrate them in place, which is the background re-encryption that ADR-0004 already scoped, not a clean start.

Revisit when the beta ends and a deliberate launch reset is on the table with the PM's consent, or when a migration genuinely cannot be expressed forward-only — at which point the choice is a real one-off negotiation, not a standing permission.
